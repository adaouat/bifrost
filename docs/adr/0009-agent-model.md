# ADR-0009: Self-agent model for SSH transport

**Status:** Accepted

## Context

v0 runs Bifrost on the target server. CI/CD is responsible for SSH transport: copying
the artifact and binary, then invoking Bifrost remotely. This works but pushes transport
complexity into every pipeline.

v1 should manage SSH itself. The client runs on a CI runner or developer machine and
drives one or more remote servers. Deployment logic (extract, link, hooks) must still
execute on the server because hooks depend on server-local context (filesystem layout,
installed services, environment variables).

Three approaches were considered:

| Approach | Description |
|---|---|
| **Pure SSH orchestration** | Encode all deployment steps as SSH commands issued from the client |
| **Dedicated agent binary** | A separate `bifrost-agent` or `bifrostd` process installed on servers |
| **Self-agent model** | Bifrost copies itself to the server and runs as its own agent |

## Decision

Use the **self-agent model**: the client uploads the Bifrost binary to the remote server
and invokes it with `--output json`. The agent is not a special mode — it is the same
binary, same commands, same atomic strategy. The only difference is that it receives a
pre-merged flat config (no `environments:` section) so no `--env`/`--app` selection is
needed.

**Client mode** is triggered when the resolved (env, app) config references at least one
server. **Agent mode** is any Bifrost invocation with a flat config (no `environments:`
key). The distinction is a loading concern, not a runtime flag.

### Client deploy flow (per server, sequential in v1)

```
1. SSH: uname -s + uname -m          → detect OS / arch
2. Local: resolve agent binary         → download from GitHub Releases if not cached
3. SFTP: upload staging dir contents:
     /tmp/bifrost-<uuid>/
       bifrost-agent                  ← the binary
       bifrost.yml                    ← flat merged config for this (env, app)
       <original-artifact-filename>   ← the artifact
4. SSH: chmod +x /tmp/bifrost-<uuid>/bifrost-agent
5. SSH: /tmp/bifrost-<uuid>/bifrost-agent deploy \
          --output json \
          --config /tmp/bifrost-<uuid>/bifrost.yml \
          --artifact /tmp/bifrost-<uuid>/<artifact> \
          [--release-name <name>]
6. Read JSON event stream → render in human/plain mode locally
7. SSH: rm -rf /tmp/bifrost-<uuid>/   ← cleanup always runs, success or failure
```

### Release name

The release name (timestamp or `--release-name` value) is generated once by the client
before the server loop starts. The same name is passed to every server agent via
`--release-name`. This ensures all servers deploy to the same release directory name,
which is essential for consistent rollbacks across a fleet.

### Release commands over SSH

`release list`, `release activate`, and `release rollback` also run through SSH in client
mode:

- `release list`: SSH to each server, run `bifrost-agent release list --output json`,
  collect and render results per server.
- `release activate`: query release lists from all servers first, present a per-server
  huh selector on the client, then run `bifrost-agent release activate <name> --output json`
  on each server with the selected release name.
- `release rollback`: run `bifrost-agent release rollback --output json` on each server.

## Rationale

**Self-agent over dedicated agent binary:**
- Single binary to distribute, maintain, and version.
- Agent always matches the client version exactly — no version skew by design.
- Existing `--output json` event stream is already the protocol; no new wire format.
- `release` commands and all future commands automatically work over SSH without extra
  agent-side code.

**Self-agent over pure SSH orchestration:**
- Hooks run with full server-local context (filesystem, environment, installed tools).
- A single SSH connection setup covers all deployment steps; no per-step reconnect.
- Complex operations (archive extraction, symlink management) stay in Go, not shell.

## Consequences

- The config loader gains a "flat" path: if no `environments:` key is present, the
  top-level config is used as-is; `--env`/`--app` are not required.
- A flat config generator is introduced on the client: it merges global < env < app and
  strips the `environments:` and `servers:` sections before writing the upload config.
- The release name must always be generated by the client in SSH mode, not inside the
  atomic strategy. The atomic strategy accepts an explicit `--release-name` (already
  implemented in M4) and uses it verbatim.
- A staging directory (`/tmp/bifrost-<uuid>/`) is created per invocation on the remote and
  always cleaned up after the agent exits, regardless of outcome.
