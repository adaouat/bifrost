# Spec 07 — SSH Transport

## Overview

When a resolved (env, app) config references at least one server, Bifrost operates in
**client mode**: it manages SSH connections itself rather than expecting to run directly
on the target server. See [ADR-0009](../adr/0009-agent-model.md) for architecture
rationale and [ADR-0010](../adr/0010-server-config-schema.md) for config schema rationale.

## Client mode detection

Bifrost enters client mode when both conditions hold:

1. The merged (env, app) config has a non-empty `servers` list.
2. At least one server name in that list exists in the top-level `servers:` map.

If neither env-level nor app-level `servers` is set, Bifrost runs in local mode (v0
behaviour, unchanged).

## Server config schema

See [Spec 02 — Configuration](02-configuration.md) for the full YAML schema. SSH-specific
fields per server entry:

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `host` | string | Yes | — | Hostname or IP address |
| `port` | int | No | 22 | SSH port |
| `user` | string | Yes | — | SSH username |
| `key_file` | string | No | — | Path to private key file. `~` is expanded. |
| `staging_dir` | string | No | `/tmp` | Base directory for the staging folder on the remote |

## Authentication

Attempted in this order; the first to succeed is used:

1. `key_file` from server config (explicit private key)
2. SSH agent via `SSH_AUTH_SOCK` socket
3. `BIFROST_SSH_PASSWORD` environment variable (password auth, all servers)

Host key verification uses the `BIFROST_KNOWN_HOSTS` environment variable when set,
otherwise the system `~/.ssh/known_hosts`. Strict verification applies either way:
unknown hosts cause an immediate failure with exit code 3, and there is no `--insecure`
bypass.

## Agent binary resolution

Before the server loop starts, Bifrost resolves the agent binary for each unique remote
OS/arch. See [ADR-0011](../adr/0011-agent-binary-distribution.md) for full details.

### Arch detection

```
SSH exec: uname -s && uname -m
```

Maps to goreleaser artifact naming:

| `uname -s` | `uname -m` | Platform key |
|---|---|---|
| `Linux` | `x86_64` | `linux_amd64` |
| `Linux` | `aarch64` | `linux_arm64` |
| `Darwin` | `x86_64` | `darwin_amd64` |
| `Darwin` | `arm64` | `darwin_arm64` |

An unrecognised combination is a fatal error (exit code 3) with a message suggesting
`--agent-binary`.

### Binary cache

```
{os.UserCacheDir()}/bifrost/agents/{version}/{os}_{arch}/bifrost
```

Cache is checked before any download. A cache hit skips the download entirely.

### Download URL

The release asset is a raw binary (no archive wrapper). A leading `v` in the version is
stripped so the release-tag path and the asset filename match goreleaser's naming:

```
https://github.com/adaouat/bifrost/releases/download/v{version}/bifrost_{version}_{os}_{arch}
```

If the release does not exist (e.g. a development build), Bifrost fails with exit code 3
and a message pointing to `--agent-binary <path>`.

### Override

The `--agent-binary <local-path>` flag on `deploy` and all `release` commands bypasses
download and cache entirely. The specified binary is uploaded as-is.

## Staging directory

Each deploy invocation creates a unique staging directory on the remote:

```
{staging_dir}/bifrost-{uuid}/
├── bifrost-agent          ← uploaded agent binary
├── bifrost.yml            ← flat merged config (no environments: or servers: sections)
└── {original-filename}    ← the artifact (deploy only)
```

`{uuid}` is a random UUID generated by the client at the start of the invocation.
`{staging_dir}` is the server's `staging_dir` field (default: `/tmp`).

### Cleanup

The staging directory is always removed after the agent exits, regardless of success or
failure:

```
SSH exec: rm -rf {staging_dir}/bifrost-{uuid}/
```

Cleanup runs even if the agent exits non-zero or the SSH connection drops after the agent
starts. If cleanup itself fails, a warning is emitted but the overall exit code reflects
the deploy result, not the cleanup failure.

## Flat config generation

Before uploading, the client generates a flat config for the agent:

1. Perform the normal 3-level merge (global < env < app) for the target (env, app).
2. Strip the `environments:` and `servers:` keys from the result.
3. Write the merged top-level fields to `bifrost.yml` in the staging directory.

The agent receives a config with no `environments:` section. The config loader detects
this and operates in flat mode: required fields are read directly from the top level and
`--env`/`--app` are not required. The client still passes `--env`/`--app` on the release
commands below for symmetry with local invocation; a flat-mode agent ignores them.

## Agent invocation

### `deploy`

```
{staging_dir}/bifrost-{uuid}/bifrost-agent deploy \
  --output json \
  --config {staging_dir}/bifrost-{uuid}/bifrost.yml \
  --artifact {staging_dir}/bifrost-{uuid}/{artifact-filename} \
  --release-name {release-name}
```

`--release-name` is always set by the client (generated once before the server loop).

### `release list`

```
{staging_dir}/bifrost-{uuid}/bifrost-agent release list \
  --output json \
  --config {staging_dir}/bifrost-{uuid}/bifrost.yml \
  --env {env} --app {app}
```

### `release activate`

```
{staging_dir}/bifrost-{uuid}/bifrost-agent release activate \
  --release {release-name} --no-confirm \
  --config {staging_dir}/bifrost-{uuid}/bifrost.yml \
  --env {env} --app {app}
```

`--release` is always set by the client (selected in the local TUI before the server loop).
`--no-confirm` makes an already-current release fail fast rather than prompt on the remote.

### `release rollback`

```
{staging_dir}/bifrost-{uuid}/bifrost-agent release rollback \
  --output json \
  --config {staging_dir}/bifrost-{uuid}/bifrost.yml \
  --env {env} --app {app}
```

## JSON event stream

The agent's stdout is a newline-delimited JSON event stream (same format as
`--output json` in local mode). The client reads it line by line and:

- In `human` / `plain` mode: renders each event as the appropriate TUI component, prefixed
  with the server name when multiple servers are involved.
- In `json` mode: re-emits each event with an added `"server"` field set to the server
  name.

Agent stderr is captured and appended to the error message on non-zero exit.

## Error handling

| Condition | Exit code | Behaviour |
|---|---|---|
| SSH connection fails | 3 | Immediate failure; remaining servers skipped in sequential mode |
| Unknown remote arch | 3 | Immediate failure before any upload |
| Agent binary download fails | 3 | Immediate failure |
| Agent exits non-zero | Forwarded | Client exits with the same code; cleanup still runs |
| Cleanup SSH exec fails | — | Warning emitted; does not change exit code |
